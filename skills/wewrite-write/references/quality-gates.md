# 质量门禁与研究核验

本文档补充五项编辑判断，不替代它。研究核验部分服务 wewrite-write 阶段的主张与来源台账；
质量门禁部分是 wewrite-review 交付前的逐项清单。编辑五项（准确、观点、有用、合声、好读）
仍是通过的主标准；`wewrite score` 只提供机械线索；门禁负责把问题定位到具体位置和严重级别。

## 研究核验

### 何时必须研究

以下内容不能只凭模型记忆：

- 新闻、热点、发布时间、价格、版本、职位、融资、市场份额和统计数据
- 产品当前能力、政策法规、平台规则、医学/法律/金融建议
- 精确数字、直接引语、争议性归因、竞品结论
- 用户提供链接或明确要求"查一下""基于最新资料"

稳定常识也要在高风险文章中复核。纯个人观点可以不搜索，但必须在 claims 中标为 `opinion`。

### 来源优先级

按以下顺序选择，重要主张尽量由两个独立来源交叉确认：

1. 法规原文、官方公告、产品文档、论文原文、财报、公开数据集
2. 当事人完整采访、机构研究、可信媒体的一手报道
3. 专业媒体、行业分析和高质量二手解释
4. 社区讨论和社交媒体：只用于发现线索或呈现"有人这样体验"，不能代表整体事实

搜索摘要不是证据。打开原页面核对标题、作者、日期、上下文和原句，注意转载、旧页面、
同源转述和内容农场。搜索摘要、模型记忆和范文一律不得标为 `verified`。

### 台账规则

对应 `claims.yaml` 与 `sources.yaml`：

- 一条主张只放一个断言；复合句拆开核验。
- `fact` 必须有能直接支持它的来源；`inference` 写出从事实到结论的推理桥；
  `opinion` 不伪装成共识；`user_experience` 只来自本次任务用户明确提供的材料。
- 来源只支持其中一部分时，缩小断言，不扩大来源含义。
- 数据写清口径、时间、样本、单位和比较基线。
- 因果表述需要因果证据；否则改成"相关""伴随""可能影响"。
- 直接引语逐字核对；无法找到原文时改为释义并注明来源。

### 专业领域复核

| 领域 | 必查项 |
|---|---|
| 商业/公司 | 财务指标口径、币种、财年、估值与融资区别、相关利益披露 |
| AI/技术 | 模型/产品准确名称、版本、发布日期、能力边界、基准条件 |
| 数据/科研 | 样本量、研究设计、相关与因果、统计显著性、论文是否被撤回 |
| 医疗 | 不做诊断替代、证据等级、适用人群、风险提示、专业人士复核 |
| 法律/政策 | 辖区、生效时间、原文条款、例外条件、非法律意见提示 |
| 金融 | 数据时点、风险、收益与回撤、非投资建议、利益冲突 |

遇到无法可靠判断的专业结论，缩小表述并在任务中标记需要领域专家终审，不用流畅文风掩盖不确定性。

### 技术与代码核验

1. 以所用版本的当前官方文档为准，不混用不同版本 API。
2. 记录版本、运行环境、依赖和命令。
3. 提取最小可运行示例，不把省略上下文的片段叫"完整代码"。
4. 在隔离临时目录实际运行或编译，验证正常路径、典型错误和边界输入。
5. 检查代码块语言标签、导入、变量名、异常处理和安全问题。
6. 文中的输出、耗时和性能数字必须来自实际执行并说明环境；否则删掉或标为未执行示意。

最低验证：Python `python -m py_compile`；JavaScript `node --check`；JSON/YAML/XML 用标准
解析器；Shell/PowerShell 做语法检查但不执行危险命令；Java 在完整项目中编译。

### 降级规则

来源不可访问或互相冲突时：

1. 保留冲突，不替用户强行裁决。
2. 优先写双方都支持的最小事实。
3. 对差异给出来源、日期和可能原因。
4. 删除无法证明且不影响主线的断言，并在任务中记录降级。
5. 在交付说明中列出仍需人工确认的主张。

## 严重级别

| 级别 | 含义 | 处理 |
|---|---|---|
| Error | 事实/代码/合规错误，或会误导读者 | 写入 `blockers`，修复前不得交付 |
| Warning | 有明显质量或可信度风险 | 修复，或在 `major_issues` 说明接受理由 |
| Note | 可选优化 | 不阻断交付 |

## 七道门禁

### G0 用户意图

- `brief.yaml` 的主题、核心判断、目标读者是否被遵守？
- `constraints.must_include` 是否仍在，`must_avoid` 是否出现？
- 篇幅、输出模式与任务书是否一致？

任一偏离为 Error。

### G1 事实与专业性

- 每个可验证主张能否映射到 `claims.yaml` 与 `sources.yaml`？
- 时效信息是否来自当前来源，日期和口径是否准确？
- 是否把观点写成事实、相关写成因果、个例写成趋势？

虚构或关键事实无来源为 Error；非关键但待核验为 Warning。

### G2 技术与代码

- API 和命令是否基于当前官方文档？
- 代码块是否按"技术与代码核验"验证，或明确标为未执行示意？
- 是否包含密钥、危险命令、注入或不安全默认值？

声称"可运行"但未验证为 Error；明确标注示意可降为 Warning。

### G3 论证与结构

- 一句话命题能否覆盖全文？每节是否推进 `brief.sections` 和对应 claim？
- 是否呈现最强合理反方，避免稻草人？
- 开头承诺是否兑现，结尾是否增加而非重复信息？
- 是否存在跳步、循环论证、口径不一致或因果倒置？

主结论无法由正文支持为 Error；冗余或节奏问题为 Warning。

### G4 文字与风格

- 是否有错别字、病句、指代不明和标点错误？
- 专有名词、英文大小写、数字和术语是否统一？
- 是否有连续套话、重复观点、句式过齐（可先运行 `wewrite score` 定位）？

影响含义的文字错误为 Error；表达问题为 Warning。

### G5 引用、版权与合规

- 引用是否必要、短小、准确并注明来源？
- 是否大段近似改写他人文章，或盗用独特结构、案例包装？
- 商业合作、赞助是否披露？是否泄露隐私、内部材料或密钥？

版权、隐私、密钥和重大合规问题为 Error。

### G6 微信呈现

- `wewrite validate` 是否通过？外链是否已转脚注、代码窄屏是否可读？
- 图片是否准确、可辨认、有授权？暗色模式是否可读？

排版导致内容缺失或错误为 Error；美观问题为 Warning。

### G7 读者终审

用目标读者视角从头读到尾：前几段是否知道为何值得读？哪里注意力断掉？能否复述一个核心判断
和一个可执行动作？标题的承诺正文是否完整交付？

## 修复与回归

1. 按 Error → Warning → Note 排序修复。
2. 一轮最多修复 3 类根因，避免全篇重写引入回归。
3. 改事实后回查标题、摘要、结尾和 `claims.yaml`；改代码后重新运行；改结构后重做
   G0、G3、G7；改风格后确认未引入事实和引语变化。
4. 最多两轮。仍有 Error 时按审稿规则删除不可靠内容、缩小承诺，交付可靠版本，不得粉饰通过。

## 报告

门禁结果并入 `assessment.yaml`：Error 写入 `blockers`，Warning 写入 `major_issues`，
`notes` 说明已执行的检查（台账回查、代码验证、validate、读者终审）和仍需确认的问题。
自检报告只保留有行动价值的条目，不输出冗长打分过程。
